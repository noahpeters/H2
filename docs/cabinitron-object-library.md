# Cabinitron Object Library

Cabinitron Core is the first object library. It registers the existing cabinet types (including open storage), appliances, bathroom fixtures, sinks, finish panels, cabinet pulls, range hoods, doors/windows/openings and island countertops. Structural room surfaces and internal assembly parts remain geometry owned by the designer.

`objectLibrary.ts` defines JSON metadata, library ownership and asset references. `coreObjectLibrary.ts` registers Core definitions and separate procedural assets. `coreObjectCatalog.ts` owns the appliance/fixture/sink dimensions consumed by both the registry and existing creation functions. `coreCabinets.ts` owns the standard cabinet templates consumed by both the registry and the designer's cabinet choices. Existing public catalog exports and selection IDs are preserved.

Each definition has a stable ID, library/tenant ownership, name/category, manufacturer/collection/SKU, source URL/format, asset IDs, dimensions, insertion origin, mounting plane/points, clearance bounds, orientation, configurable dimensions, finishes, tags and visibility. Unknown manufacturer data and clearances are null; empty mounting points mean unspecified. Empty finishes mean the existing material controls remain responsible for appearance. Dimensions are defaults, not constraints on a placed instance. Generated pulls, hoods and openings depend on their host or room. Insertion origins describe the catalog coordinate convention; procedural renderers continue to own their assembly transforms.

Designer metadata uses inches, X width, Y up and Z depth with front toward +Z. Orientation is Euler degrees, following the existing designer yaw convention. Imported geometry must be normalized to GLB in meters; metadata stays outside the file. The source format can retain STEP/OBJ/FBX/glTF provenance while `canonicalAssetId` points at a GLB asset. Core objects currently have `canonicalAssetId: null` and an explicit `proceduralAssetId`: no existing procedural geometry has been baked or falsely labeled as GLB. Resizing, cabinet internals, motion, finishes, room-dependent shower height and placement keep their existing implementations.

`coreObjectForElement` and `coreObjectForOpening` resolve old and new rooms from existing semantic fields. Scene objects and sink/pull/hood subassemblies expose only `{libraryId, objectId}` under `userData.objectLibrary`. Changing an element type resolves its new identity. Published custom cabinets and design-specific configurations keep their existing snapshot model and are not incorrectly assigned to Core. Room format version 2 is unchanged; no storage migration is needed because references are derived rather than persisted redundantly.

Tenant libraries have `scope: 'tenant'` and a tenant ID. Definitions and canonical assets must match that ownership. `visibleLibraryObjects` supports explicitly enabled Core and owner libraries; it is a selection helper, not a security boundary. Future storage APIs must authorize the tenant server-side, including private asset retrieval. `objectDefinitionErrors` checks already typed records for ownership, finite dimensions/coordinates, ordered bounds and asset-reference consistency; it is not an untrusted-upload parser or GLB binary validator.

This foundation does not add upload endpoints, conversion jobs, storage tables, renderer loading of arbitrary GLBs or manufacturer catalogs. Those can use the new schema without changing the current designer. A future ingestion pipeline must validate/normalize uploaded GLBs or tessellate other formats, store the resulting GLB, validate metadata and authorize tenant/library ownership before publishing a definition. GLB-only runtime records avoid adding a separate renderer for each source format.
